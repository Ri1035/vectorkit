# 为什么转得这么快？加时间有用吗？—— 实测回答

> 触发问题：**"为什么我的转矢量处理那么快？把处理时间适当加长，效果会好一些吗？"**
> 方法：搭测量台，在无头 Edge 里跑真实 WASM 管线，**测真实耗时 + 质量（MSE / PSNR）**。
> 日期：2026-10-12　状态：**结论已验证，尚未改代码**

---

## 一、结论摘要

1. **为什么快**：我们的管线是**单遍前馈**（预处理 → VTracer → SVGO → 后处理），**没有任何迭代优化循环**；
   而 VTracer 官方明确说它**跳过了 Potrace 的"最优多边形搜索"**，换取线性时间。**不是代码更优，是算法类别不同。**
2. **单纯"加时间"完全无用**：管线里没有"可迭代的目标函数"，多等一秒，输出一个像素都不会变。
3. **把时间投到"更高分辨率 / 迭代优化"上有用，而且效果显著**：实测**上采样 ×2 → MSE −42%、PSNR +2.36 dB**（代价约 +200ms）。
4. **但边际收益递减，且"时间≠质量"**：好的预处理反而**更快且不差**（去噪+平滑：时间 ×0.61，MSE 基本不变）。
5. **这个杠杆你马上就能用**：预处理面板里的 **「小图自动上采样」**（已存在，默认关闭）。

## 二、实测数据（512×384 合成图：圆 / 旋转矩形 / 6px 细线 / 5 个小点，含真实抗锯齿）

| 配置 | 预处理 | 引擎 | **合计** | anchors | bytes | **MSE ↓** | **PSNR ↑** |
|---|---|---|---|---|---|---|---|
| A 基线（不做预处理） | 1ms | 90ms | **210ms** | 112 | 3.5KB | **76.4** | 29.30 dB |
| B + 中值去噪 | 62ms | 48ms | **131ms** | 122 | 3.7KB | 78.1 | 29.20 dB |
| C + 去噪 + 保边平滑 | 83ms | 28ms | **128ms** | 104 | 3.2KB | 74.6 | 29.40 dB |
| **D + 上采样 ×2** | 272ms | 141ms | **431ms** | 871 | 23.1KB | **44.3** | 31.66 dB |
| E = D + `simplify 1` | 297ms | 126ms | **434ms** | 278 | 7.2KB | 46.0 | 31.51 dB |
| **F `vmde` 档**（cutout + simplify 1） | 256ms | 150ms | **422ms** | 563 | 16.1KB | **41.4** | **31.96 dB** |

**相对 A 基线的变化**

| 配置 | 时间 | MSE | PSNR | 体积 | 锚点 |
|---|---|---|---|---|---|
| B 去噪 | **×0.63** | +2.2% | −0.10 dB | ×1.07 | ×1.09 |
| C 去噪+平滑 | **×0.61** | −2.4% | +0.10 dB | ×0.92 | ×0.93 |
| **D 上采样×2** | ×2.05 | **−42.0%** | **+2.36 dB** | ×6.61 | ×7.78 |
| E D+simplify1 | ×2.07 | −39.8% | +2.21 dB | ×2.07 | ×2.48 |
| **F `vmde` 档** | ×2.01 | **−45.8%** | **+2.66 dB** | ×4.63 | ×5.03 |

> 读数要点：
> - **D/B/C 对比**：B、C 花时间去噪平滑后，**总时间反而更短**（引擎要处理的东西变少了）——说明"时间"不是质量的代理变量。
> - **D 是质变点**：像素量 ×4，MSE 近乎腰斩。这是"花时间换质量"**唯一被实测证实的强杠杆**。
> - **E 是划算的**：在 D 基础上加 `simplify 1`，**时间几乎不变**（434 vs 431ms），
>   **锚点 −68%、体积 −69%**，MSE 只从 44.3 涨到 46.0（+3.8%）——**用极小质量代价换回巨大体积/节点收益**。
> - **F 最均衡**：MSE 41.4（比 D 还好）、PSNR 最高、体积 16.1KB。

## 三、为什么我们的管线这么快（根因）

```
我们的：预处理 → VTracer（线性 O(n)、跳过最优多边形搜索） → SVGO → 后处理   ← 单遍前馈，无循环
Vector Magic：抗锯齿生成模型 → 离散阶段 → 【非线性共轭梯度迭代】→ 贝塞尔拟合
              ↑ 上万连续变量 + 十万级离散变量，反复"重渲染→算误差→求梯度→更新"
```

- VTracer README 原话：**"skips Potrace's expensive optimal-polygon search in favor of a fast, linear pipeline"**。
- 我们的后处理（D-P 抽稀、低通平滑、圆/椭圆拟合、边界吸附）**都是一次性遍历**，没有"再评估、再修正"的回路。
- **所以快不是因为写得好，而是因为做的事少**：一次成型 vs 全局迭代。

## 四、"加时间"的正确姿势（三类杠杆）

| 类别 | 手段 | 实测/预期收益 | 代价 | 现状 |
|---|---|---|---|---|
| **① 提高输入分辨率** | 小图上采样 ×2（`upsample`） | **MSE −42%、PSNR +2.36 dB**（实测） | 时间 ×2、体积 ×6.6、锚点 ×7.8 | ✅ **已可用**（预处理面板「小图自动上采样」） |
| **② 迭代优化（真正的"用时间换质量"）** | 重栅格化误差优化（v4.7 设计） | 迭代越多误差越低，**边际递减**；目标是再压 MSE | 每次迭代都要重渲染 | ⛔ 未实现 |
| **③ 降低有损捷径** | 关掉预处理量化（`maxColors`）、提高 `colorPrecision`、降 `filterSpeckle` | 保色/保细节，收益取决于图 | 色块/节点变多 | ⚠️ 部分可用 |
| ❌ 纯延时 | sleep / 人为等待 | **0**（管线无可迭代目标） | — | 无意义 |

**关键区分**：**"加时间"本身不是目的，"增加可迭代的优化步数 / 提高采样分辨率"才是手段。**
一旦迭代收敛（或达到收益阈值），继续加时间就只剩"更慢"，没有"更好"。

## 五、现成可用的最大杠杆（今天就能试）

预处理面板 → **「小图自动上采样」**（短边 < 800px 的小图，描摹前放大 2×）
- **效果**：边缘台阶宽度减半 → MSE −42%、PSNR +2.36 dB（实测）
- **代价**：约 +200ms；节点数 ×7.8（可用「细节保留度」补偿）；体积增大
- **建议**：Logo / 印章 / 插画等小图**开启**；本身就是大图（短边 ≥800px）**不适用**（开关不生效）

## 七、阶段 1 已落地（v4.7）

- 面板新增 **「描摹分辨率」**（关闭 / 自动（小图 ×2，默认）/ ×2 / ×3），并加 **8M 像素安全预算**
  （超出自动降倍并在状态行说明）。
- **Bon Cho 1280² 实测**：×2 → MSE **51.52 → 24.15（−53%）**、PSNR **+3.29 dB**、白缝/白点 11 → 7；
  代价：约 +1.3s、体积 ×3.2。
- **引擎边界**：**3840²（14.7M 像素）输出退化**（大面积白色覆盖内容）；2560²（6.55M）正常 →
  故设 8M 像素预算；小图（512×384）×3 正常且最佳。

## 八、测量方法（可复现）

```bash
# 1) 启动测量服务（静态托管 + 接收报告）
node scripts/_e2e-serve.cjs 5199
# 2) 无头 Edge 打开测量页（注意：不加 --virtual-time-budget，才能测到真实耗时）
"C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe" --headless=new --disable-gpu \
  --user-data-dir=/tmp/q-prof "http://127.0.0.1:5199/scripts/_e2e-quality.html"
# 3) 报告落在 E:\Wb\rea-vm-analysis\out\e2e-report.json（页面 POST /report 回传）
```

- 质量口径：把输出 SVG 用 resvg **栅格化回原尺寸** → 白底合成 → 与原图**逐像素比 RGB** → MSE / PSNR。
- 该口径正是 v4.7「重栅格化误差优化」的**目标函数**，测量台可直接复用。
