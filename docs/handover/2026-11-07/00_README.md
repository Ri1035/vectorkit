## 一句话结论

**不能。这条路已经走到头了。**

在 VTracer 的输出上做任何非零强度的几何平滑，都会降低精度——已经用 9 组实验 + 1 组零权重对照证明。

---

## 关键数字（1280² 口径，白底合成，逐像素 RGB）

| 方案 | 段数 | PSNR | edgeCorr |
|---|---|---|---|
| VTracer `spline`（现用） | 1493 | 32.88 | 0.765 |
| VTracer `polygon` 原样 | 4832 | 33.29 | 0.793 |
| polygon + rdp0.35 + 手柄拟合 | 4006 | **33.34** | 0.793 |
| polygon + rdp1.5 + 手柄 | 1830 | 32.03 | 0.723 |
| **四项能量优化（w_len=5, w_prior=1）** | 2707 | **31.99** | 0.718 |
| **优化（w_len=0.1, w_prior=0.01）** | 2730 | **32.04** | 0.737 |
| **亚像素目标 + 联合优化** | 2939 | **30.41** | 0.625 |
| **优化（w=0，零权重对照）** | 4006 | **33.34** | 0.793 |

零权重那行与"不优化"**逐字节相同**——所以掉分来自平滑本身，不是实现 bug、不是参数没调好。

---

## 为什么

VTracer 的 `polygon` 输出是**像素级精确**的边界点（每个点都落在真实边界上）。
平滑的本质是"把点从当前位置推走"，在没有更准的目标位置时，**推走 = 损失**。

Vector Magic 需要平滑，是因为它的分割边界有噪声（锯齿、毛刺）。
VTracer 的输出没有这个噪声——它内部已经做过 contour 简化。

**两者输入的前提不同，把后者的手段搬到前者上必然负收益。**

---

## 该做什么（按性价比排序）

### ✅ 1. 停止在几何后处理上投入

`subpixel.js`、`refine.js`、以及任何"移动锚点"的方案，在扁平插画上都不成立。
项目 `app.js:1053` 那条"cutout 下必须跳过几何后处理"的注释，其实可以推广到**所有情况**。

### ✅ 2. 若非要压段数：用 polygon + 容差拟合，别用平滑

```
VTracer polygon (pathPrecision 2)
  → Douglas-Peucker eps≈0.35
  → 角点分段（转角 > 100°）
  → 每段 Schneider 开放拟合
```
本轮的 `rdp + 手柄` 拿到 33.34 dB / 4006 段，但**体积 181 KB**（spline 只有 34 KB）。
只有当"精度优先、不在乎体积"时才值得——项目已确认体积不设约束，所以**可行**，但要接受 5× 体积。

> 若要更少段数，得把拟合器做好：本轮的 Schneider 实现在闭合点列上崩了（17.56 dB），
> 原因是没做角点分段。`vectorkit/bezierfit.js` 已经是对的（角点断点 + 开放段拟合），
> 直接复用它，不要重写。

### ✅ 3. 真正还剩下的方向（都不便宜）

| 方向 | 说明 | 成本 |
|---|---|---|
| **重写分割** | 现在的 4.8 dB 差距根在这里。VM 是"抗锯齿生成模型的 MAP 反解"，VTracer 是"颜色聚类 + 轮廓追踪"。要追就得换引擎 | 数月 |
| **超分后再描摹** | 项目已测：×2 得 +3.15 dB，但仍差 4.8。可以试 ×3/×4 + 更好的上采样 | 数天，早前测过收益递减 |
| **接受差距** | 33 dB 对扁平插画已是可印刷质量；VM 的 39 dB 是"像素级复刻原图"，不一定是用户要的 | 0 |

---

## 不该做什么（已验证无效）

- ❌ 在 VTracer 输出上做变分平滑 / 蛇形优化 / 能量最小化
- ❌ 逐点亚像素重定位（项目 v5.2 失败，本轮 81% 点被判可移动 → 30.41 dB）
- ❌ 用 `simplify` 压体积（项目已测降质，本轮容差扫描复现同一趋势）
- ❌ 用降噪换平滑（项目 v5.3 已踩：PSNR +2.86 但观感变差）
- ❌ 重写 Bézier 拟合器（`bezierfit.js` 不比 VM 差）
