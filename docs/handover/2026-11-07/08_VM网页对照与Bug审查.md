## 二、为什么它看起来更平滑、更精细

### 2.1 机制差异（已逆向确认）

| 环节 | Vector Magic | 我们（VTracer + 后处理） |
|---|---|---|
| 范式 | **MAP 反问题**：把「矢量 + 抗锯齿光栅化」建成可微模型，迭代求最优 | 单遍前馈：颜色聚类 → 轮廓追踪 → 曲线拟合 |
| 边界定位 | **反解覆盖率 → 亚像素边界**；相邻区域**联合求解**，天然共用同一条曲线 | 引擎按区域独立描边，再用拟合器贴合 |
| 颜色 | **逐区域解最优色**（同一张图会出现 `#fffffd`/`#fefefe` 多个近似白） | 引擎聚类，不做逐区域优化 |
| 节点 | 节点 + 双侧手柄，**相邻句柄拉成共线（C1）**，角点用硬切线 | 贝塞尔拟合（Schneider / 手柄），段间 C1 靠拟合器近似 |
| 平滑能量 | 四项能量：弧长归一化二阶差分 + **L1 转角** + 气压 + **0.7px 死区鲁棒数据项** | 无迭代；靠 `simplify` / 边缘平滑档位 |

关键一条：VM 的 **L1 转角**（`|û−v̂|`）对「90° 角」和「5° 抖动」收同样的单价，
而抖动是一串点、角是一个点 → **角留下、阶梯消失**。这是「又平滑又保角」的数学来源。

### 2.2 但它并不是「不丢失」——我们实测过

v6.8b 对 VM 导出的 `bc.svg` 做 3× 局部放大逐点核对：

- VM **丢掉了**字母 B/o 的孔洞、眼睛高光、鼻孔
- 我们（去噪 4 + simplify 0）**全部保留**
- 同图同口径：VM PSNR 39.15 / ssimEdge 0.450；我们 36.11 / **0.486**

v7.0 的逐像素分解进一步说明：**99.25% 像素完全相同**，差距集中在 **2.2% 的边缘过渡带**
（差 84%）与内部色块（16%，且**我们颜色更准**：0.94 vs 1.13）。

### 2.3 那为什么「看起来」VM 更精细？

因为**碎块**与**过渡带**：

| 现象 | VM | 我们 |
|---|---|---|
| 物件数 | 66 path / 54 group（大量子路径塞进复合路径） | 一色一形状，anti-alias 过渡色各自成小路径 |
| 边缘过渡带 | 亚像素求解，边界一条干净曲线 | 拟合 + 平滑，仍可能残留 1–2px 台阶 |
| 小碎片 | 直接丢弃 | **保留**（于是看起来「碎」） |

本轮实测我们默认档在 bc-test 上的碎片构成：67 条路径里有 **16 条 ≤8 节点**，
填充色是 `#DBBBAC` / `#D4A786` / `#EACEAE` 这类**彼此极近的过渡色** —— 它们不是噪声，
而是原图抗锯齿边的真实颜色，所以量化掉就会「丢细节」，保留就会「碎」。

**这就是两难的根**：VM 选择「丢小碎片换干净」，我们默认选择「保小碎片换保真」。

### 2.4 可执行的三条逼近路径（按性价比）

| # | 做法 | 预期 | 代价 |
|---|---|---|---|
| 1 | 继续降 `filterSpeckle`（8→6→4） | 细节更全、白缺失更少（9551→8805→7914） | 对象数 67→95→161 |
| 2 | 提高 `colorPrecision` 到 7–8 并关闭 `simplify` | 过渡色更细、边更顺 | 体积与对象数上升；v7.1 实测 8 会降 PSNR |
| 3 | 真正的解法：**逐区域颜色求解 + 过渡带几何精修** | 才可能同时「少碎片 + 不掉细节」 | 需重写后处理，属月级工程；v7.0 已判定「预期收益极低」 |

**已提供的折中**：v8.2 新增「易编辑（叠加）」模板（`stacked`），编辑时移动单块不露白。

## 三、全面 Bug 审查

### 3.1 动态：四个功能页全链路（Edge headless）

| 用例 | 结果 |
|---|---|
| Tab1 位图→矢量（bc-test，默认档） | ✅ 49.9 KB / 95 路径 / 2142 节点 / 414 ms，下载 SVG 51,127 B |
| Tab2 矢量→位图（上一步的 SVG） | ✅ 2560×2560 / 191.5 KB / resvg / 220 ms |
| Tab3 优化压缩（同上 SVG） | ✅ 49.9 → 30.3 KB（−39.3%）/ 56 ms |
| Tab4 去背景（内置示例） | ✅ 480×480 / 23.7 KB / 72 ms |
| 控制台错误 / 页面异常 | **0 条** |
| 上传非图片（README.md） | ✅ 提示「请选择图片文件」，不崩溃 |
| 把位图当 SVG 传给 Tab2 | ✅ 提示「这不是一个有效的 SVG 文件」 |
| 空 `<svg>`（无任何图形） | ❌ **原实现会「成功」导出一张空白图** → 已修 |

### 3.2 已修（v8.3）

| 严重度 | 位置 | 问题 | 修法 |
|---|---|---|---|
| 中 | `app.js` `loadSvgForRaster` / Tab3 载入 | 空 `<svg>` 会被当作有效文件，渲染出空白图并允许下载，用户无法判断是文件本身没内容 | 新增 `hasDrawable()` 检查，无 `path/rect/text` 等元素时明确报错 |

### 3.3 已登记、未修（需产品决策或较大改动）

| 严重度 | 位置 | 问题 | 现状 |
|---|---|---|---|
| 中 | 全局错误提示 | 用 `alert()` 弹模态，阻塞页面，且不留痕 | 建议改结果区内联错误条（UX 变更） |

## 四、下一步建议

1. **先定取舍**：「保细节」还是「少碎片」——这决定默认档往哪边偏，不能同时最大化
2. 若要更接近 VM 的观感：试「去噪 6 + 简化 0.5 + 层差 32」，看 161 条路径在你眼里是否可接受
3. 若碎片是主要痛点：用「易编辑（叠加）」或「节点精简」模板
