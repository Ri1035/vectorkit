# 阶段 0 · 卡死与长任务审查（2026-11-07）

> 触发：用户要求「先进行阶段 bug 审查，检查有没有卡死情况」。
> 方法：静态审查（全部 `while`/递归/await 点）+ 浏览器实测（Edge headless + CDP Profiler）。
> 环境：本机 `node scripts/serve.mjs 5188`，Edge（Playwright `channel: 'msedge'`），headless。

## 一、结论先行

**没有发现死循环或永久卡死。** 所有循环都有退出条件，所有 await 都能落到 catch。

**发现 3 个「会表现为卡死」的真实隐患**，其中 2 个已修复：

| # | 隐患 | 触发条件 | 表现 | 处置 |
|---|---|---|---|---|
| R1 | 转换链路加载引擎无超时 | 弱网/代理让同源请求挂起 | 按钮永久停在「转换中…」且不可点，无报错、无重试 | ✅ 已修（v7.9） |
| R2 | Paper.js `<script>` 加载无超时 | 脚本既不 onload 也不 onerror | 停在「加载几何引擎」，转换永不结束 | ✅ 已修（v7.9） |
| R3 | 模板点击可重入转换 | 转换进行中点模板 | 两次并发跑，后完成者覆盖结果（可能是旧配置） | ✅ 已修（v7.9） |
| R4 | 主线程长阻塞 | 密集线条图（自动 ×2 上采样） | 单次连续阻塞 **1.2–1.3 s**，期间 UI 完全不响应 | ⚠️ 保留（见第三节） |
| R5 | 错误路径用 `alert()` | 转换失败 | 模态框阻塞页面，无内联错误位 | ⚠️ 保留（低优先） |

## 三、实测：长任务与热点

### 3.1 主线程阻塞实测

| 图 | 尺寸 | 总耗时 | 最长连续阻塞 | 热点（自身耗时） |
|---|---|---|---|---|
| mandala | 366×375（自动 ×2 → 732×750） | 1515 ms | **1202–1300 ms** | VTracer WASM 792 ms、`medianFilter` 144 ms、`getImageData` 68 ms、`protectInteriorElements` 44 ms |
| bc-test | 1280×1280 | 759 ms | 未出现独立长任务（<200 ms 分段） | `medianFilter` 239 ms、VTracer WASM 217 ms、`protectInteriorElements` 62 ms |

**判定**：阻塞主要来自 **VTracer 的同步 WASM 调用**（单次不可切分），其次是中值滤波。
这不是 bug，但用户会感知为「点了没反应」。

**为什么 mandala 比 1280² 的 bc 还慢**：mandala 是密集细线图，段数极多（783 条路径 / 18341 节点），
且短边 < 800 触发自动 ×2 → 实际描摹 732×750。**耗时由内容复杂度决定，不只是像素数。**

### 3.2 稳定性实测

| 场景 | 结果 |
|---|---|
| 冷启动 → 引擎就绪 | 169 ms → 227 ms，`VTracer 就绪` |
| 单次转换（mandala） | 1649 ms 完成，按钮恢复可点，无 console error / pageerror |
| 转换中连点 4 个模板 | 最终按钮 `开始转换`、无 spinner、结果正常、零报错（修复前也侥幸恢复，但存在覆盖风险） |
| 关掉「同色合并」重测 | 1234 → 1313 ms，**几乎无变化** → 长阻塞不在后处理，而在引擎 |

## 四、已实施的修复（v7.9）

### R1 · 引擎加载超时

新增 `loadEngineWithTimeout(name, label)`：包一层 20 s `withTimeout`，**超时后清空该引擎的缓存槽**
（`slot.loading = null; slot.mod = null`），使下一次点击能重新加载而不是复用一个永远 pending 的 promise。

`vectorize()`（vtracer / potrace / imagetracer）与 `svgoOptimize()` 全部改走该入口。
`warmup()` 原本已有超时，保持不变。

### R2 · Paper.js 加载超时

`loadPaper()` 加 15 s 超时：超时后 `s.remove()` + `paperPromise = null` + reject，
调用侧已有「Paper.js 加载失败，已跳过同色合并」的降级分支 → 转换继续，不卡死。

### R3 · 转换重入保护

```js
let vectorRunActive = false;
let vectorRunPending = false;
```
- 进行中再次请求 → 只置 `pending`，不并发
- 结束后若有 pending → 补跑一次（用最新配置）
- 顺带修掉 `busy()` 被调用两次导致按钮 innerHTML 还原错乱的可能

### 回归守护

`npm test` 新增「卡死防护」5 项断言（源码级）：
`vectorize` / `svgoOptimize` 必须走带超时的加载、`loadEngineWithTimeout` 必须存在、
`loadPaper` 必须带超时、`runVectorize` 必须有重入保护。

## 五、保留项与后续建议

### R4 · 主线程长阻塞（不建议现在动）

VTracer 的 WASM 调用是**同步**的，无法在 Promise 层切分。可选方向：

| 方案 | 代价 | 备注 |
|---|---|---|
| Web Worker 承载引擎 | 高 | 项目 v0.2 已实测「module worker 内 import 永远挂起」，需要改成 classic worker + inline blob 才能绕开，风险大 |
| 预处理分块让出主线程 | 中 | `medianFilter` / `protectInteriorElements` 可每 N 行 `await yieldFrame()`，能削掉约 200 ms，但拿不到引擎那 0.7 s |
| 仅加「处理中」提示 | 低 | 现状已有进度条，但阻塞期间进度条不刷新，用户看不出在动 |

**建议**：先记录现状（最长阻塞约 1.2–1.3 s / 密集线条图），等用户实际反馈「大图卡住」时再投 Worker。

### R5 · `alert()` 错误提示

转换失败用 `alert` 会阻塞页面。建议改成结果区内的内联错误条（与 `#epsStatus` 同风格）。
属 UX 变更，与本次卡死无关，先登记。
