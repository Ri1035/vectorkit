## 一、拆解报告里真正有价值的 5 个发现

### 1. 数学核心外包给 BLAS/LAPACK（最重要的技术信号）

报告显示 `lapack_win32.dll`（3.79MB，1291 个导出）+ `blas_win32.dll`（640KB，141 个导出）——
**矢量化的数学计算（最小二乘、矩阵分解、曲线拟合）全部走业界标准数值库，不是自研**。

**对 vectorkit 的启示**：
- 我们 v2.6 的 `fitCircleShapes()` 用手写的 Kåsa 最小二乘解圆拟合——**路线完全一致** ✓
- 下一步扩椭圆/圆角矩形拟合时，优先继续"标准数学方法 + 自研小实现"：纯前端场景拒绝引入大型数值库
  （ml-matrix 一类会增加 30KB+ 体积，而我们需要的算法每个约 100 行）
- 唯一值得借鉴的进阶是**抗噪**：真实图片里"近似圆但边缘有噪点"的情况，Kåsa 对离群点敏感，
  可加一步 RANSAC 式抽样验证（成本约 50 行）

### 2. "只锁核心"的保护策略

主程序 `vmde.exe` 与 `QtCore4.dll` 加壳（节名混淆 / VMProtect），其余 DLL 全部裸奔。

**解读**：商业软件把保护预算集中在"许可校验 + 核心算法所在的两个文件"上。这说明他们的
**核心资产 = 算法实现**。对 vectorkit 的对应物就是 `merge-paths.js`（圆拟合 / 曲线拟合 /
碎块清理 / 同色合并）与 `eps-export.js`（CMYK EPS）——**这就是我们的护城河**。
当前开源策略下不需要保护，但"哪部分是核心资产"这个判断值得记住。

### 3. 技术栈 15 年未大改（Qt4 + VS2003，2010 编译，仍在卖 $295）

**双面解读**：
- 正面：算法稳定性本身就是价值（十几年不重写也能持续收款）
- 反面：创新停滞，正是被自家 Vectorizer.AI（深度学习路线）取代的原因

**对 vectorkit**：我们相对它的结构性优势不是某个参数，而是**每一轮都能做量化对比的系统迭代能力**
（v2.6 的四轮实验 + CHANGELOG 记录与否决原因）。这条要保持。

### 4. `imageformats` 目录 → 直接暴露功能缺口

该目录含 `qjpeg4.dll` / `qtiff4.dll` ——**Qt 图片格式插件**。其中 TIFF 是关键：

| 格式 | Vector Magic 桌面版 | vectorkit 现状 |
|---|---|---|
| PNG / JPG / GUI / BMP | ✓ | ✓ |
| **TIFF**（印刷/扫描行业标准）| ✓ | **✗ 缺失** |
| AI（.ai）输出 | ✓ | ✗ |
| **DXF 输出**（切割机/激光/CNC）| ✓ | **✗ 缺失** |

Qt 的插件式架构提示：图片格式支持应当**可插拔**（按需加载解码器，不拖累主包）——
vectorkit 若加 TIFF，同样应做懒加载（仅在上传 TIFF 时才加载解码器）。

### 5. 平台矩阵差异（顺带记录）

桌面版独有：批量处理、离线、AI/DXF 输出；在线版独有：最新的处理引擎。
vectorkit 是纯前端，**天然具备"离线 + 本地隐私"**，缺的是**批量处理**与**更多输出格式**。

## 二、从 REA 项目学到的方法论

**REA（github.com/morluto/rea）**：MIT 许可，把 AI agent 接到 Ghidra/Hopper/IDA，
用三段式流程调查软件功能：**decompile（恢复可读证据）→ understand（追踪理解）→ recreate（为你的项目实现）**。

三个可借鉴的原则：

1. **证据化结论**：它的每个判断都附证据与局限声明。这与我们 v2.6 的做法一致
   （CHANGELOG 记录每轮实验的参数、结果、**否决原因**）——继续保持，并考虑把实验流程工具化
2. **能力边界诚实声明**：REA 明确说"不恢复原源码、不克隆应用"。vectorkit 的 README「能力边界」章节同理 ✓
3. **本地化分析**：REA 强调全程本地不上传——与 vectorkit 的隐私定位完全同源，可作为宣传点

**合规提醒**（写进计划避免以后踩线）：REA 自身也强调不绕过技术保护措施（DMCA 1201 同类约束）。
本次拆解止于 PE 构成与公开功能，**不做脱壳、不提取算法实现**。

## 三、vectorkit 优化计划（按优先级，待确认后实施）

### P0 — 高价值、成本可控

| # | 项目 | 说明 | 预估改动 |
|---|---|---|---|
| 1 | **直线规整（正交吸附）** | 近似水平/垂直的边吸附到精确角度（图稿本应是笔直的）；延续 v2.6 几何基元路线 | merge-paths.js +80 行 |
| 2 | **DXF 输出** | 切割机/激光/CNC 场景刚需；DXF 是文本格式（LWPOLYLINE/SPLINE 实体），可复用现有路径数据 | 新模块 dxf-export.js ~200 行 + UI 导出按钮 |

### P1 — 明显增益

| # | 项目 | 说明 |
|---|---|---|
| 3 | 椭圆拟合 + 等半径统一 | Kåsa 推广到椭圆；同一图内相同半径的圆统一半径（设计意图还原） |
| 4 | TIFF 输入 | 懒加载解码器（含 LZW/Deflate/PackBits），印刷扫描场景 |
| 5 | 批量处理 + ZIP 打包 | 桌面版独有能力，纯前端可做（多文件队列 + 打包下载） |

### P2 — 精细化

| # | 项目 | 说明 |
|---|---|---|
| 6 | 圆角矩形识别 | 4 直线 + 4 圆角的标准图元重建 |
| 7 | 参数实验流程工具化 | 把 v2.6 的"多候选并行渲染 + dataURL 提取 + 目检"固化为 scripts/_bench，供每轮迭代复用 |
| 8 | 抗噪圆拟合（RANSAC） | 提升真实拍摄/压缩图片上圆拟合的成功率 |

### 明确不做

- 逆向 Vector Magic 的算法实现（合规边界）
- 脱壳 / 绕过保护措施
- AI 矢量化路线（既定决策：维持"纯本地 + 免费 + 印刷 EPS"定位）

## 四、建议的下一步

1. 从 **P0-1 直线规整** 开始（延续已验证成功的几何基元路线，风险最低、与用户场景最贴合）
2. 其后做 **P0-2 DXF 输出**（打开"切割/激光"新场景，是桌面版与我们的最大功能差距）
3. 每轮沿用 v2.6 的验证方法：多候选对比 + 量化指标 + CHANGELOG 记录（含否决原因）
