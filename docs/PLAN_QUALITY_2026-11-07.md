# 质量回归诊断与改进计划（2026-11-07）

> 触发：用户实测四个问题 —— ① 碎块多 ② 边缘白边化、锯齿明显 ③ 丢失多 ④ 色块没有合并。
> 并追问：这是「Web 端难实现」还是需要「纯本地桌面化」。
> 本文只做诊断与计划，**不含代码改动**。

---

## 一、先回答：不是 Web 的问题

| 疑问 | 结论 |
|---|---|
| 是不是浏览器算力不够导致质量差？ | **不是**。质量差来自**算法取舍与后处理**，不是平台。四个问题都能在浏览器里修 |
| 要不要改成桌面程序（Electron/Tauri/WinUI）？ | **不需要**。桌面壳只解决「打包/文件系统/多线程」，不改变描摹质量 |
| 什么情况下才需要本地化？ | 只有三种：① 超大图（>2400px、>20M 像素）想常驻内存；② 想用多线程 Worker 并行；③ 想直接读写本地目录/批量。这些都可以用 **WASM + Worker + File System Access API** 在 Web 内实现 |

关键证据：VM 的网页版与桌面版**跑的是同一套引擎**（同为 MAP 反问题 + 共轭梯度），
网页版质量并不低于桌面版 —— 说明这套算法在浏览器里是可行的。
我们与它的差距在**算法层**（分割 + 联合边界求解），不在运行环境。

> 唯一真正的 Web 限制是「主线程会被同步 WASM 阻塞 1.2–1.3s」（v7.9 已记录）。
> 这是**体验**问题，可用 Worker 解决，与画质无关。

## 二、四个问题的根因（都有数据）

### ① 碎块多

- bc-test 1280² 实测：默认档 67 条路径，其中 **16 条 ≤8 节点**
- 这些小路径的填充色是 `#DBBBAC` / `#D4A786` / `#EACEAE` / `#E7CEB0` 等
  —— **彼此极近**的过渡色，来自原图的抗锯齿边
- 现有的合并只处理「颜色几乎相同」的路径（`mergeSameColorPaths` 按 fill 分组），
  **不会把 ΔE 很小的相邻色块并成一块**

→ 根因：缺少「近似色区域合并」与「小区域并入邻色」

### ② 边缘白边 + 锯齿

- 白边量化：`seam` 指标 = 参考图有色、输出接近纯白的像素数
  - 默认档（去噪 10）：**9551 px**；去噪 8：8805；去噪 4/16：7279
- 成因有两层：
  1. **背景白块**：输出里有一条 `#fdfdfd` 路径（207 节点，全图最大），
     它的抗锯齿边缘会压在相邻色块上 → 视觉白边
  2. **过渡带**：VTracer 的区域边界落在「抗锯齿中点」，两侧各留 0.5px 半透明过渡，
     重栅格化后就是一圈浅色晕

→ 根因：背景层未分离 + 边界没有做「过渡带归属」处理

### ③ 丢失多

- 去噪 10 是实测中**丢细节最多**的一档（v8.2 已回调到 8）
- 再往下降（6/4）细节回来，但碎块成倍增加
- 说明当前「去噪」是一个**面积阈值**，无法区分「噪点」与「设计细节」

→ 根因：碎块清理按**面积**判定，而非**对比度 × 面积**

### ④ 色块没有合并

- 现有 `mergeSameColorPaths` 只在**颜色完全相同（容差 0.5）**的路径间做布尔并集
- 描摹输出里同一视觉色的多个区域常带 ±2~3 的色差 → 不被视为同色 → 不合并
- 且 `cutout` 模式下几何后处理被跳过（保共享边），进一步限制了合并

→ 根因：合并判据是「精确同色」而不是「视觉同色」

## 三、改进计划（按性价比排序）

### Phase 1 · 纯后处理修复（小工作量，直击四个问题）

**1-A 近似色区域合并**（解决 ①④）

- 把 fill 按 Lab ΔE ≤ 3 聚类为「视觉同色」，同簇内做 Paper.js 并集
- 再把「面积 < 阈值 × 且与邻居 ΔE ≤ 2」的小区域直接并入该邻居的颜色
- 验收：bc-test 路径数 **95 → ≤45**，同时 PSNR 不下降

**1-B 背景层分离**（解决 ② 的一半）

- 识别「近白 + 覆盖画布 >90%」的路径，作为背景层单独处理：
  - 默认**不导出**（页面预览本身有白底，效果不变）
  - 或导出为最底层并裁掉 0.5px 内缩，避免抗锯齿边压在图形上
- 验收：`seam` 从 8805 → **<1500**

**1-C 过渡带归属（去白晕）**（解决 ② 的另一半）

- 描摹前预处理：对「与两侧色差都 ≤ 阈值」的 1px 过渡像素，
  强制归到**较近的一侧色**（而不是插值色）——减少引擎产出中间色
- 验收：白边像素再降 50%，且眼白/鼻孔仍在

**1-D 对比度感知碎块清理**（解决 ③）

- 已有 `isHighContrastDetail`（面积小 + 与周围色差 ≥60 → 保留）
- 把它接成默认开启，并把判据从「面积」改为「面积 × 对比度」
- 验收：碎块数下降的同时，眼睛高光/鼻孔**不丢**

### Phase 2 · 并列引擎接入（中等工作量）

- 把已完成的 `subpx.js`（marching squares + 覆盖率亚像素）+ `bezierfit.js` 接成可选引擎
- 现状：几何已验证（bc 1024² 32.04 dB），但**未做颜色区域合并**，节点数 7244
- 需要补：区域合并 + P2' 容差寻优，才有机会超过 VTracer
- 验收：同图 PSNR ≥ VTracer +0.3 dB **且** 节点数 ≤ VTracer

### Phase 3 · 自研分割（大工作量，VM 路线）

- 调色板聚类 → 区域合并 → 联合边界求解（覆盖率场）→ 手柄几何
- 这是唯一能同时做到「少对象 + 少碎片 + 不掉细节 + 无白边」的路线
- 成本与风险最高，建议 Phase 1/2 完成后再评估

## 四、验收指标（每个 Phase 结束必须同时给出）

| 指标 | 现状（bc-test 1280²） | Phase 1 目标 |
|---|---|---|
| PSNR | 33.23 | **≥ 34.0** |
| 白边/缺失像素（seam） | 8805 | **< 1500** |
| 路径数 | 95 | **≤ 45** |
| ≤8 节点的小路径 | 67 | **≤ 10** |
| 眼白 / 鼻孔 / 字母孔洞 | 保留 | **保留**（目检 + ROI MSE） |
| 单次连续阻塞 | 1.2–1.3 s | 不变（本轮不碰引擎） |

> 纪律：任何“更好”的结论必须同时给客观指标 + 至少一个观感代理，且逐区域不得变差。

---

## 五、建议

**先做 Phase 1**。四条都不动引擎、不改架构，全部在后处理/预处理层，
且直接对应你提的四个问题；做完你再用 bc-test 目检一次。

如果 Phase 1 后仍觉得「不如 VM 干净」，那才需要决定要不要投 Phase 3（月级工程量）。

至于「纯本地桌面化」——**不建议**。它解决不了这四个问题，只会增加维护成本。

Phase 1 的 1-A / 1-B / 1-D 已落地；1-C 未做。修复了 7 个管线冲突（详见
[`AUDIT_PIPELINE_2026-11-07.md`](./AUDIT_PIPELINE_2026-11-07.md)）。

| 配置（bc-test 1280²） | PSNR | seam | 路径数 |
|---|---|---|---|
| v8.5 默认 | 33.07 | 7392 | 94 |
| **v8.6 默认（近似色合并开）** | **33.04** | **7380** | **53** |
| 关闭近似色合并 | 33.06 | 7392 | 94 |
| 全部后处理关闭 | 33.22 | 8824 | 95 |

未达成的目标：PSNR ≥34.0、seam <1500。seam 的剩余部分来自 VTracer 的区域边界
（两侧各 0.5px 抗锯齿过渡），属于引擎层，不在 Phase 1 可修范围。

顺带修复的既有 bug：小图 ×2 上采样只输出左上角 1/4（`ensureSvgSize` 的 viewBox 与显示尺寸混用），
修复后 winter / sunflower / mandala 分别从 10.62 / 9.67 / 8.41 dB 提升到 30.08 / 24.83 / 19.28 dB。
